# hiring-traps

공공기관 채용공고 스무 건을 재료로 Upstage Studio 를 재본 기록이다. 노드가 몇 종이고 무엇이 실제로 쓰이는지, 같은 문서를 두 번 넣으면 값이 얼마나 갈리는지, 손으로 짠 것과 자동 생성이 어떻게 다른지를 쟀다.

## 원래 만들려던 것과 달라졌다

시작은 도구였다. 채용공고에서 사람이 읽어도 놓치는 줄을 뽑으려 했다.

자격 기준일이 접수마감일인지 최종시험일인지, 우대인 줄 알았는데 필수인 항목, 가점이 중복되는지 택일인지, 서류 발급에 며칠 걸리는지.

파이프라인은 돌아간다. 그런데 도구가 되려면 하나가 더 있어야 한다. **그 줄이 어디에 있었는지** 다. 첫 쪽 요약표에 큰 글씨로 적힌 기준일은 아무도 안 놓친다. 함정이 되려면 각주나 괄호 안이어야 한다.

추출 결과에는 쪽 번호만 오고 그 줄이 각주인지 괄호인지가 안 담겼다. 위치를 재는 코드는 따로 있는데(`probe/locate.py`) 손으로 만든 어휘 목록으로 줄을 찾아서 추출 결과와 안 이어져 있었다.

**그 조각은 2026-09-03 에 붙였다**(`probe/where.py`). 이제 인용마다 그 줄의 글자 크기와 세로 위치와 각주 표시가 나온다 — 어휘 목록 없이, 기계가 낸 인용으로.

그런데도 「숨어 있나」에는 아직 못 간다. 작은 글자나 괄호 안이 곧 함정이라는 근거가 없기 때문이다. 그걸 재려면 지원자가 실제로 무엇을 놓쳤는지를 알아야 하고 그 자료가 없다.

그래서 이 저장소가 지금 가진 것은 **분포와 자리**다. 그 정보가 문서에 있는지, 있다면 어디에 있는지까지고, 그 자리가 함정인지는 아니다. 이름은 그대로 두되 첫 줄을 고쳤다.

## 잰 것 — Studio

노드가 몇 종인지 문서에서 못 찾아 API 를 찔렀다. 없는 종류를 넣으면 서버가 전부 나열해 준다. **열넷이다.**

    class-generate · class-update · document-classify · document-parse · export
    information-extract · instruct · instruct-generate · match · merge · review
    schema-generate · schema-update · validate

그런데 내 계정 에이전트 열아홉 개가 실제로 쓴 것은 넷뿐이었다. extract 34 회, parse 19 회, classify 14 회, instruct 8 회. 나머지 열 종은 0 이다.

parse 가 열아홉인 것은 에이전트마다 하나씩 있기 때문이고, extract 가 서른넷인 것은 한 에이전트에 여러 개가 붙기 때문이다. 읽는 노드는 겹쳐 쓰고 나머지는 안 쓴다.

안 쓰이는 쪽에 파이프라인을 닫는 것들이 몰려 있다. 검사(`validate`), 사람 검토(`review`), 내보내기(`export`), 쪼개고 합치기(`split` + `merge`).

나도 그 함정에 두 번 빠졌다.

28 쪽 공고문이 모델에 부담이라 판단해 PyMuPDF 로 일곱 쪽씩 잘라 넣었고, 조각마다 분류를 다시 타서 다섯 중 셋이 거절됐다. 나중에 `document-classify` 에 `split` 옵션이 있는 것을 알고 켜보니 28 쪽 중 1~15 쪽만 공고문 구간으로 잡았고 토큰을 20% 덜 썼다.

나는 쪽수로 잘랐고 Studio 는 내용으로 잘랐다.

스키마도 같았다. 문서 셋에 손으로 라벨을 달아 필드 다섯 개를 설계하는 데 한 시간 반을 썼는데 `schema-generate` 가 같은 문서에서 33 초에 24 개를 냈다.

그중 하나는 내가 놓친 것이었다 — 최종 발표 뒤의 이의제기 기한이다. 넣고 스무 건에 다시 돌리니 열여섯 건에서 나왔다.

## 잰 것 — 편차가 어디서 오나

같은 문서를 두 번 돌리면 값이 다르게 나온다. 텍스트가 한 글자도 다르지 않고 바이트만 다른 파일 두 개에서 기준일 개수가 1 과 13 으로 갈렸다.

원인이 두 곳이었다. 파싱의 `ocr: auto` 가 파일이 바뀌자 다른 판단을 내렸고, 값을 고정하니 토큰 편차가 34% 에서 2% 로 줄었다.

그런데 같은 파일을 반복해서 돌릴 때의 흔들림은 그대로 남는다. 자격 항목이 7 과 23 을 오갔다.

두 번째는 모델 탓이 아니라 내 스키마 탓이었다. 「인사규정 결격사유를 자격 항목으로 볼 것인가」를 안 정해줘서 판마다 다르게 정했다. 경계를 명시하니 7 · 6 · 7 로 모였다.

세 번째 층은 성격이 다르다. 추출 결과의 인용이 원본 PDF 에 글자 그대로 서는지 스무 건 793 칸에 대고 대조해봤더니, 못 찾은 칸이 **107 에서 550 사이**를 오갔다. 대조 전에 무엇을 지우는지와 fitz 에게 쪽을 어떤 순서로 읽게 하는지, 내가 고르는 것 둘에 따라 움직인다. 어느 칸도 정확도라고 부르지 못했다.

**이 수는 모델이 인용을 안 지킨 비율이 아니다.** 대조 대상인 fitz 텍스트도 원문이 아니라 두 번째 추출기의 출력이라, 둘이 다를 때 어느 쪽이 원문인지 이 대조는 모른다. 여덟 칸 전부와 근거는 [docs/variance.md](docs/variance.md) 「세 번째 층」에 있다.

## 잰 것 — 억지로 답하지 않는다

입찰 문서용으로 만든 에이전트에 채용공고를 넣어봤다. 세 건 모두 `OTHER_REVIEW_REQUIRED` 를 확신도 0.99 로 내놓고 분류에서 멈췄다. 추출은 돌지 않았다.

반대 경우를 생각하면 값이 보인다. 잘못 분류했다면 추출이 「입찰 참가자격」을 찾으러 돌았을 것이고, 그럴듯한 값이 나왔을 것이고, 틀렸다는 것을 아무도 몰랐을 것이다.

## 세기 전에 다섯 번 틀렸다

함정을 한 건도 안 셌는데 측정 장치가 다섯 번 틀렸다.

함정 어휘를 머리로 만들어 서른여섯 쪽 공고문에서 넷이 0 건이었고, 표본을 앞에서부터 받아 스무 건 중 열다섯이 병원이었고, 첨부의 첫 PDF 를 집어 직무기술서가 표본에 들어왔고, 목록 한 쪽의 타임아웃 하나가 수집 전체를 죽였고, 「중복지원 불가」가 「가점 중복 배제」로 잡혔다.

마지막 것은 뜻이 정반대다.

전부 [docs/phase0-notes.md](docs/phase0-notes.md) 에 그대로 적었다.

## 잰 것 — 인용이 어디에 앉아 있나

원문에 서는 인용 622 칸이 PDF 줄에 어떻게 앉는지 쟀다. 317 칸은 한 줄 안에 통째로 있고 305 칸은 여러 줄에 걸친다.

여기서 손잡이가 셋 더 늘었다 — 걸친 인용의 자리를 첫 줄로 잡을지 가장 작은 줄로 잡을지(두 규칙이 갈리는 것 51 칸), 같은 문장이 여러 곳에 나올 때 어디를 쓸지(34 칸), 한 줄에 들어가는데 이어붙이면 걸치는 경우(2 칸). 전부 고르지 않고 나란히 적었다.

그리고 `probe/locate.py` 가 `hidden_mark` 하나로 묶어 둔 여섯 표시를 갈라 보니 **괄호가 절반이었다.** 622 칸 중 괄호가 312, `※` 가 46, `*` 가 43 이고 괄호밖에 없는 것이 258 칸이다. 괄호는 어느 문서에나 있으니 「숨어 있다」의 근거로는 약하다.

작은 글자나 각주 표시가 곧 함정이라는 근거는 아직 없다. 그걸 재려면 지원자가 실제로 무엇을 놓쳤는지를 알아야 하고 그 자료가 없다. → [docs/where.md](docs/where.md)

## 안 한 것

사람이 들고 갈 한 장을 만드는 코드가 없다.

겹침 판정에 오탐이 남아 있다 — 「구조화금융」이 직무명인데 자격 겹침으로 잡혔다. 서류 개수는 파싱을 고정해도 20 · 13 · 17 로 흔든다.

## 돌리는 데 필요한 것

파이썬 3, PyMuPDF, 그리고 Upstage API 키.

```bash
pip install pymupdf
```

키는 `.env` 에 `UPSTAGE_API_KEY=` 로 넣는다. 이 파일은 저장소에 없다. 받은 PDF 도 없다 — `docs/phase0-manifest.json` 에 기관명과 파일 번호와 sha256 이 있어 같은 파일을 다시 받는다.

```bash
python probe/collect.py 20                       # 표본을 다시 받는다
python agent/build_agent.py                      # 정의를 만든다
python agent/push.py                             # 계정에 올린다
python probe/studio_run.py fixtures/live/<번호>.pdf <agt_...>
python probe/judge.py <추출결과 여럿>              # 합치고 판정한다
python probe/node_contracts.py                   # 노드 계약을 캔다
```

키를 안 쓰는 것도 있다. 저장된 출력과 PDF 만 읽는다 — 다만 PDF 는 저장소에 없으니 위 `collect.py` 를 먼저 돌려야 한다.

```bash
python probe/recheck.py                          # 인용이 원문에 서는지 대조한다
python probe/where.py                            # 그 인용이 어디에 앉아 있는지 본다
python probe/compare.py                          # 골든셋과 나란히 놓는다
python probe/locate.py                           # 후보 줄의 위치를 잰다
```

`agent/deployed.json` 에 올라가 있는 에이전트와 설정 ID 가 있다. 에이전트는 계정에 붙어 있고 기기에 안 붙어 있어서 다른 기기에서 그대로 쓸 수 있다.

윈도우에서 만들었다. 맥에서는 `python` 을 `python3` 으로 바꾼다. 리눅스는 확인하지 않았다.
