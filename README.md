# hiring-traps

공공기관 채용공고에서 사람이 읽어도 놓치는 줄을 뽑는다. Upstage Studio로 문서를 읽고, 판정은 코드가 다시 센다.

## 지금 상태

함정을 아직 세지 않았다. 공고문 스무 건을 모았고, 세 건에 손으로 정답을 달았고, 그 셋에 에이전트를 돌려 대조했다.

채용공고는 다섯 쪽이면 사람이 삼 분에 읽는다. 그래서 읽어주는 도구는 값이 없고, 값이 있는 자리는 읽고도 놓치는 몇 줄이다. 자격 기준일이 접수마감일인지 최종시험일인지, 우대인 줄 알았는데 필수인 항목, 가점이 중복되는지 택일인지, 서류 발급에 며칠 걸리는지.

넷 다 아직 가설이다.

## 세기 전에 다섯 번 틀렸다

함정을 한 건도 안 셌는데 측정 장치가 다섯 번 틀렸다. 함정 어휘를 머리로 만들어 서른여섯 쪽 공고문에서 넷이 0건이었고, 표본을 앞에서부터 받아 스무 건 중 열다섯이 병원이었고, 첨부의 첫 PDF를 집어 직무기술서가 표본에 들어왔고, 목록 한 쪽의 타임아웃 하나가 수집 전체를 죽였고, 「중복지원 불가」가 「가점 중복 배제」로 잡혔다.

마지막 것은 뜻이 정반대다.

전부 [docs/phase0-notes.md](docs/phase0-notes.md)에 그대로 적었다.

세기 전에 도메인 사실도 나왔다. 공고 서른세 건을 살펴 스무 건을 건졌고 열세 건은 건너뛰었다. 첨부가 아예 PDF가 아니거나(아홉 건) 붙은 PDF가 직무기술서였다(네 건). 공공기관 채용공고를 기계로 읽으려면 상당수는 애초에 읽을 물건이 아니다.

## 에이전트를 만들어 돌렸고, 기계가 나를 세 번 고쳤다

채용공고용 에이전트를 코드로 정의해 계정에 올리고, 손으로 라벨을 단 세 문서에 돌렸다.

기계가 라벨러보다 나은 곳이 셋이었고 전부 원문으로 다시 확인했다. 가점 상한 10% 조항을 내가 놓쳤고, 「가점 규칙이 없음」과 「있는데 불분명함」을 잘못 갈랐고, 같은 시점이라도 걸리는 대상이 다르면 다른 줄이라는 것을 뭉갰다.

기계가 틀린 곳은 하나다. 1쪽에서 필수라고 한 자격을 3쪽에서 우대라고 부르는 문서가 있는데, 두 쪽에 흩어진 그 모순을 잇지 못했다. 세 문서를 통틀어 UNCLEAR 판정이 한 번도 안 나왔다.

한 번은 내가 기계를 틀렸다고 볼 뻔했다. 같은 조항이 두 줄로 나와 중복 추출인 줄 알았는데, 원문이 그 조항을 두 자리에 적어놓은 것이었다.

자세한 것은 [docs/phase1-comparison.md](docs/phase1-comparison.md)에 있다.

## 튜닝 네 갈래를 재봤다

낮은 모델에서 최선을 뽑는 방법을 넷 놓고 하나씩 쟀다. 파싱 옵션 고정, 여러 판 합치기, 문서 쪼개기, 필드 분리다.

가장 싼 것이 가장 크게 이겼다. 파싱이 `ocr: auto` 였는데, 텍스트가 한 글자도 다르지 않고 바이트만 다른 파일 두 개에서 토큰이 34% 갈렸다. 값을 고정하니 2% 로 줄었다.

쪼개기와 필드 분리는 값을 못 했다. 쪼개기는 두 배 시간을 쓰고 편차 안쪽 변화만 얻었고, 필드 분리는 자격 항목이 절반으로 줄면서 비용만 40% 늘었다. 「긴 문서가 부담이다」와 「한 호출에 다섯 필드가 부담이다」는 둘 다 이 문서들에서 전제부터 틀렸다.

여러 판 합치기는 목표를 이뤘다. 프롬프트로 세 판을 고쳐도 못 잡던 모순을 코드가 한 번에 잡았다.

자세한 것은 [docs/tuning.md](docs/tuning.md)에 있다.

## 판정을 모델에서 떼어냈다

Studio 는 뽑기만 하고 판정은 뒤에서 한다. 겹침을 찾는 것은 코드가 하고, 그 겹침을 문서가 이미 정리했는지만 Solar 에게 묻는다. 집합 연산을 모델에 맡기면 편차만 들어오고, 「이 줄이 그 겹침을 정리한 것인가」는 언어를 읽어야 안다.

그렇게 하니 판정이 결정적이 됐고 왜 그렇게 찍혔는지 설명이 된다. 항목마다 세 판 중 몇 판에서 나왔는지도 붙는다. 1/3 과 3/3 은 같은 값이 아니다.

옮기고 나서 배운 것이 하나 있다. **판정을 코드로 옮기면 편차는 사라지지만 버그는 조용해진다.** 모델은 틀리면 이상한 답을 내놓는데 코드는 0 건을 내놓고, 그것은 「없다」와 구분되지 않는다. 첫 실행이 0 건이었고 그것이 내 조사 제거기 버그였다. 정답을 아는 사례를 하나 박아둬서 잡혔다.

## Studio는 억지로 답하지 않았다

새 에이전트는 API로 못 만들고 Studio UI에서 가져오는 길밖에 없다. 그래서 먼저, 다른 프로젝트에서 쓰던 입찰 자격 에이전트에 채용공고를 그대로 넣어봤다.

세 건 모두 `OTHER_REVIEW_REQUIRED`를 확신도 0.99로 내놓고 분류 단계에서 멈췄다. 뒤 단계는 돌지 않았다.

도메인이 다른 문서를 아는 갈래로 우겨넣는 대신 사람에게 넘긴 것이다.

반대 경우를 생각하면 이게 왜 값이 있는지 보인다. 채용공고를 제안요청서로 잘못 분류했으면 추출 단계가 「입찰 참가자격」을 찾으러 돌았을 것이고, 그럴듯한 값이 나왔을 것이고, 틀렸다는 것을 아무도 몰랐을 것이다.

## 스무 건을 훑은 결과

| 함정 | 문서 수 |
|---|---|
| 자격 항목 · 제출서류 | 20/20 · 20/20 |
| 자격 기준일 | 16/20 |
| 가점 중복 규칙 | 16/20 |
| 발표 후 기한 | 15/20 |
| 가점 조건 | 9/20 |

「발표 후 기한」은 마지막에 넣은 여섯째 함정이다. `schema-generate` 노드를 돌려봤더니 자동 생성 스키마에 이의제기 기한 필드가 있었고 내 다섯 필드에는 없었다. 넣자마자 넷 중 셋꼴로 나온다.

이 수를 두 번 못 박아 둔다. **한 번 돌린 값이다.** 같은 문서를 다시 돌리면 개수가 흔들린다. 그리고 **「있다」이지 「숨어 있다」가 아니다.** 원래 세기로 한 것은 자리가 나쁜 것만인데, 추출 출력에 그 줄이 각주인지 괄호인지가 안 담긴다. 그래서 이 표는 분포이지 함정 개수가 아니다.

## 돌리는 데 필요한 것

파이썬 3, PyMuPDF, 그리고 Upstage API 키.

```bash
pip install pymupdf
```

키는 `.env`에 `UPSTAGE_API_KEY=`로 넣는다. 이 파일은 저장소에 없다. 받은 PDF도 없다 — `docs/phase0-manifest.json`에 기관명과 파일 번호와 sha256이 있어 같은 파일을 다시 받는다.

```bash
python probe/collect.py 20                       # 표본을 다시 받는다
python agent/build_agent.py                      # 정의를 만든다
python agent/push.py                             # 계정에 올린다
python probe/studio_run.py fixtures/live/<번호>.pdf <agt_...>
python probe/judge.py <추출결과 여럿>              # 합치고 판정한다
```

`agent/deployed.json`에 지금 올라가 있는 에이전트와 설정 ID가 있다. 다른 기기에서는 계정이 같아도 그 ID가 그대로 쓸 수 있다 — 에이전트는 계정에 붙어 있고 기기에 붙어 있지 않다.

윈도우에서 만들었다. 맥에서는 `python`을 `python3`으로 바꾼다. 리눅스는 확인하지 않았다.
